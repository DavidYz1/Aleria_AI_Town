# Phase 1E：内容圣经与提交叙事 Design Spec

> 状态：Proposed，等待人工 Review
>
> 日期：2026-08-24
>
> 依据：腾讯 AI 小镇作业要求、现有项目文档、Phase 1D 稳定版本、《剧情.docx》及本轮确认的叙事决策

## 1. 阶段定位

Phase 1E 不扩张 World、Player、Quest 或 Chat 的核心状态机，而是为已经跑通的游戏闭环建立一套可持续维护的内容基线，并将项目整理成评审者能够快速理解、启动和体验的提交作品。

本阶段需要同时解决两个问题：

1. **游戏内部讲什么故事**：统一世界历史、玩家身份边界、NPC 人设、知识差异、地点气质和任务伏笔。
2. **提交材料如何讲清这个项目**：让 README 先呈现玩法、人物和体验，再说明启动方式、技术架构、AI/Mock 模式与工程过程。

Phase 1E 的原则是：**增强内容表现，不虚构尚未实现的玩法；丰富角色智能，不破坏确定性世界引擎。**

## 2. 当前工程基础

Phase 1D 完成后，项目已经具备以下可运行闭环：

- World Tick 与 NPC Action 保持确定性；
- 世界包含星辉酒馆、中央公园、晨曦城堡、低语森林；
- Ryan、Shir、Grey 具有基础状态、行为规则与可查看详情；
- 玩家可以在地点间移动；
- 玩家可以接取并完成“寻找失踪孩子”任务；
- Quest 交互检查玩家、任务阶段、地点及目标 NPC 是否在场；
- NPC Chat 支持 Mock 与 OpenAI-compatible Provider；
- Chat 失败时安全降级至 Mock；
- Chat 只读取世界上下文，不修改 World Tick、NPC State、Action、Event 或 Quest；
- Backend、Frontend 与相关自动化测试均已形成稳定基线。

因此，本阶段不重新设计既有架构，而是在这些边界上补足内容、表达和验收材料。

## 3. 本阶段目标

### 3.1 内容目标

- 建立唯一可信的中文 Story Bible；
- 统一艾莱瑞亚、曦谷、晨曦城堡等正式术语；
- 解决“五百年前战争”与 Grey 个人经历之间的时间线冲突；
- 让 Ryan、Shir、Grey 在立场、语言、秘密与矛盾上具有明显区分；
- 为失忆玩家建立足够明确、但不会提前揭底的叙事钩子；
- 让现有失踪孩子任务自然触碰主线谜团，而不增加新的任务状态；
- 让 Mock 模式下的常见问答也符合人物设定。

### 3.2 提交目标

- 将 README 重组为“游戏体验优先、工程说明随后”的提交首页；
- 清晰覆盖题目要求中的玩法与 NPC 设定、技术选型、接口与决策流程、安装启动、AI/Mock 模式、AI 工具使用及人工修正案例；
- 明确区分当前功能与未来规划；
- 补充经过脱敏的真实模型配置建议；
- 将 `hy-role` 表述为“基于本项目角色对话实测的推荐模型”，并在后续加入一个经过确认的短对话示例。

### 3.3 工程目标

- 保持现有 API、数据库模型和核心状态机不变；
- Prompt 内容继续版本化，旧版本可回退；
- 内容增强具有自动化测试或明确的人工验收项；
- 每个开发模块都可独立 Review 和提交；
- Codex 不自动执行 Git Commit。

### 3.4 腾讯作业要求对齐

| 作业关注点 | 当前基础 | Phase 1E 的贡献 |
| --- | --- | --- |
| 小镇玩法与 NPC 设定 | World、Player、Quest、3 名 NPC 已可交互 | 用 Story Bible 和角色知识边界说明“为什么值得交互” |
| NPC 行为与决策 | 确定性 Tick、Decision、Action、Event 已完成 | 保持机制不变，在文档中清楚展示决策流程 |
| NPC AI 对话 | Mock、真实 compatible Provider、Fallback、聊天保存已完成 | Prompt v3、角色化 Mock、`hy-role` 推荐提升展示效果 |
| 前后端闭环 | Vue 与 Backend API 已跑通 | 用 README 重组体验路径与启动说明 |
| 技术选型与接口 | 架构、API、数据库文档已存在 | 从提交首页建立清晰索引，减少技术文档堆叠感 |
| AI 工具使用与人工修正 | 已有 `hy-role` 输出解析修正案例 | 将真实案例整理成可审阅、不过度包装的说明 |

Phase 1E 不以新增系统数量为目标，而是把已完成能力、内容特色和工程判断准确地呈现给评审者。

## 4. 非目标

Phase 1E 明确不实现以下内容：

- 不新增 Player 职业选择、姓名输入或身世分支；
- 不实现故事结局选择、阵营选择或分支任务；
- 不新增 Quest 状态、Quest 类型或第二条任务链；
- 不引入 Relationship、复杂 Memory、RAG 或长期记忆；
- 不允许 Chat 改变世界或任务状态；
- 不修改 World Tick、NPC 决策和 Action 执行模型；
- 不新增数据库表或修改 API 契约；
- 不在本阶段实现 PixiJS、Cocos 或像素地图；
- 不在 README 中宣称已经实现上述未来功能；
- 不在本阶段完成云部署、Docker 或线上体验地址。

像素地图与场景交互属于 Phase 2，部署与最终提交资产属于后续交付阶段。

## 5. 核心叙事命题

艾莱瑞亚的核心问题是：

> 如果一个建立在谎言之上的和平确实保护了无数普通人，揭穿它仍然天然正确吗？

作品不把冲突简化为“人类邪恶、古族正义”。古族希望限制力量以保护正在衰竭的世界本源；人类则依靠魔法维持防御、医疗、生产和文明秩序。立即停止扩张可能拯救遥远的未来，也可能先摧毁当下无数人的生活。

伊萨尔采取了极端手段，试图通过摧毁人类魔法文明阻止世界继续衰亡。他既不是官方历史中的纯粹恶魔，也不是应被无条件歌颂的救世主。人类联盟赢得战争、改写历史并维持了五百年的秩序，但其和平建立在被封存的牺牲和违背的盟约之上。

曦谷的日常温暖、可亲和安全感必须真实存在。黑暗背景不是为了否定小镇生活，而是让玩家逐渐意识到：**值得保护的生活和必须面对的真相可能同时成立。**

## 6. 正史时间线

### 6.1 远古黄金时代

人类、精灵、矮人与后来被称为“古族”的长生种共同生活。古族能够感知世界本源，并主张力量必须受到约束；人类凭借学习、改造和规模化使用魔法迅速建立文明。

### 6.2 终焉战争：约五百年前

世界本源因长期消耗而衰弱。古族领袖伊萨尔要求人类限制魔法扩张，人类联盟认为这将断送文明和现实中的无数生命。谈判失败后，伊萨尔试图摧毁人类魔法体系，终焉战争爆发。

战争最终进一步撕裂世界本源。部分古族以自身作为“锚”修补裂隙，幸存者与人类建立最后盟约。战后统治者为避免秩序崩塌，将伊萨尔塑造成堕落魔王，将古族统一称作恶魔，销毁记录并封印遗迹。

### 6.3 被遗忘的五百年

官方历史成为共同常识，古族幸存者退入荒野、地下与伪装身份。有人只希望活下去，有人守护真相，也有人继承伊萨尔对人类的敌意。人类社会在不完整的历史上继续繁荣。

### 6.4 灰烬战争：约二十余年前

人类对终焉战争遗迹的重新勘探触碰了尚未稳定的封印。一次原本受控的调查迅速演变为局部战争，被后世称为“灰烬战争”。它没有揭开完整真相，只留下更多被封存的档案、失踪者和无法解释的痕迹。

Grey 参与的是这场战争及相关遗迹行动，而不是五百年前的终焉战争。他在行动中失去同伴，也因此比普通人更清楚官方叙事并不完整，但仍不知道全部真相。

### 6.5 现在

曦谷坐落在终焉战争遗迹与灰烬战争旧封锁区附近。表面上，它是一座从战争阴影中恢复过来的安静小镇；地下和森林深处仍保留着世界本源、古族盟约以及历史改写的痕迹。

一名失去记忆的旅人带着无法解释的印记在曦谷醒来。游戏当前章节从一次普通的失踪事件开始。

## 7. 正式术语与命名

以下词汇作为当前中文内容的唯一标准写法：

| 类别 | 正式名称 | 使用说明 |
| --- | --- | --- |
| 世界 | 艾莱瑞亚 | 不再混用“阿莱瑞亚”等译名 |
| 小镇 | 曦谷 | 所有玩家可见内容统一使用 |
| 酒馆 | 星辉酒馆 | 任务起点与玩家初始活动中心 |
| 公共区域 | 中央公园 | 保留现有名称 |
| 城堡 | 晨曦城堡 | 不使用“曦谷城堡”等变体 |
| 森林 | 低语森林 | 遗迹和任务线索所在地 |
| 远古冲突 | 终焉战争 | 约五百年前 |
| 近代冲突 | 灰烬战争 | 约二十余年前 |
| 被抹去种族 | 古族 | 官方文本可能贬称其为恶魔 |
| 古族领袖 | 伊萨尔 | 官方历史中的“魔王” |

稳定的程序 ID、API 字段值和数据库标识不因中文文案调整而变化。

## 8. 信息分层与防剧透边界

世界观不应作为一个完整长文本直接塞入每次模型请求。Phase 1E 采用四层信息结构：

### 8.1 Author Truth

只存在于 Story Bible 和开发文档中的完整真相，包括终焉战争的真实原因、最后盟约、历史改写和主线长期方向。

Author Truth 不直接作为运行时 Chat Prompt 输入，也不直接写入 README 的无剧透介绍。

### 8.2 Public Lore

曦谷普通居民能够知道的官方历史和日常信息：人类联盟击败魔王、灰烬战争留下创伤、森林遗迹危险、晨曦城堡保存旧档案等。

Public Lore 进入世界 Prompt，并可由所有 NPC 自然谈及。

### 8.3 Character Knowledge

每位 NPC 分别维护以下边界：

- 确认知道什么；
- 怀疑什么；
- 错误相信什么；
- 刻意隐瞒什么；
- 在当前章节绝不能说出什么。

角色只能根据自己的知识层回答，不能因为模型读过世界设定就变成全知叙述者。

### 8.4 Player Context

运行时只向 Chat 提供当前玩家已知事实和现有状态，例如当前位置、任务阶段、近期事件以及玩家醒来时便拥有的印记。

尚未被任务揭示的信息不得伪装成玩家已经知道的事实。

## 9. 玩家设定

当前玩家仍使用既有 `default-player`，不新增职业、属性或身世字段。

玩家的固定叙事事实为：

- 在曦谷附近醒来；
- 失去此前记忆；
- 身上存在一个无法解释的印记；
- 不确定自己的姓名、来历、职业和立场；
- NPC 默认称其为“旅人”或根据对话自然称呼。

印记是全局叙事事实，不是当前数据库中的可装备道具，也不触发独立能力。它在现阶段只作为玩家身份谜团与遗迹主线之间的连接点。

以下内容保持未定义，直到未来章节需要时再决定：

- 玩家真实身份；
- 印记的最终来源；
- 玩家是否与古族、盟约或世界本源直接相关；
- 最终是否允许公开真相、维持沉默或选择第三条道路。

## 10. NPC 内容圣经

### 10.1 Ryan：相信英雄的人

**表层身份**：年轻骑士，热情、直接，渴望证明自己能够保护别人。

**鲜明特征**：相信英雄叙事，却害怕史莱姆；行动经常快于思考。

**内在矛盾**：他真心相信正义，也真心相信官方英雄史，但父亲曾因保护一名被称为“恶魔”的幸存者而被视为叛徒。

**角色需求**：他需要决定正义来自权威授予，还是来自亲眼看到的人与事。

**知识边界**：熟悉公开历史和骑士传说，不知道终焉战争真相；会本能为父亲辩护，却无法解释父亲当年的选择。

**语言风格**：短句、坦率、有行动感；紧张时会逞强，不使用学术化长篇解释。

### 10.2 Shir：把真相当作武器的人

**表层身份**：冷静的侦察者与信息搜集者，熟悉森林路线和隐秘行动。

**鲜明特征**：观察敏锐、戒备心强，对甜食有不符合外表的偏爱。

**内在矛盾**：她认为真相不应被埋葬，却知道未经准备的真相可能伤害今天无辜的人。

**角色需求**：她必须判断玩家是可以托付线索的人，还是又一个会滥用历史的人。

**知识边界**：知道官方历史存在删除痕迹，并接触过守护禁忌资料的隐秘组织；不知道全部 Author Truth，也不会初次见面就交出核心秘密。

**语言风格**：克制、精确、带试探；很少直接下结论，更倾向用反问和细节判断对方。

### 10.3 Grey：用沉默保护和平的人

**表层身份**：资深守护者，沉稳可靠，在曦谷具有威望。

**鲜明特征**：习惯先确认风险再行动，对年轻人的冲动既严厉又包容。

**内在矛盾**：他知道被维护的和平并不完全诚实，却亲眼见过真相碎片引发的死亡。

**角色需求**：他必须重新判断沉默究竟是在保护小镇，还是只是在延续旧日错误。

**知识边界**：经历灰烬战争与遗迹调查，知道档案被封、历史有矛盾；没有经历五百年前的战争，也不知道终焉战争完整真相。

**语言风格**：简洁、谨慎、有分量；不会轻易许诺，不主动进行全知式世界观讲解。

### 10.4 NPC 之间的关系张力

- Ryan 尊敬 Grey，却可能无法接受 Grey 对父亲事件的沉默；
- Grey 希望保护 Ryan，也担心他的英雄理想会将他带向旧日悲剧；
- Shir 认为 Grey 知道得比他说出的更多，因此既利用他的经验也不完全信任他；
- Ryan 觉得 Shir 冷淡而可疑，但在危险环境中承认她非常可靠；
- 三人都可能帮助玩家，但理由和愿意承担的代价不同。

Phase 1E 只将这些关系用于角色表达，不新增数值化 Relationship 系统。

## 11. 现有任务与主线衔接

“寻找失踪孩子”的流程和状态保持不变：

1. 玩家在星辉酒馆接取任务；
2. 前往晨曦城堡，与在场的 Grey 交谈；
3. 前往低语森林调查；
4. 发现孩子留下的鞋；
5. 返回星辉酒馆完成任务。

本阶段只增强叙事表达：

- Grey 提醒玩家孩子失踪地点接近灰烬战争旧封锁线；
- 鞋附近存在一个被灼烧的古老符号，与玩家身上的印记具有相似轮廓；
- 孩子可能提到林中听见无法辨认的低语或歌声；
- 任务完成时，居民把它视作一次普通救援，但玩家得到“自己的失忆可能与此地有关”的第一个私人疑问。

该伏笔不得直接证明玩家身份，不解锁新任务，不改变现有 Quest 状态数量，也不让 NPC 立刻掌握完整答案。

## 12. Prompt v3 设计

Phase 1E 计划新增 `prompts/v3/`，保留 v1、v2 作为可回退版本。

建议结构保持当前 Loader 能力范围：

```text
prompts/v3/
├── chat_system.md
├── world_lore.md
├── player_context.md
└── characters/
    ├── ryan.md
    ├── shir.md
    └── grey.md
```

设计要求：

- `world_lore.md` 只包含 Public Lore、地点氛围和当前时代常识；
- `player_context.md` 只定义失忆、印记及不可擅自补全的边界；
- 角色 Prompt 各自携带知识范围、误解、隐瞒、语言风格和关系张力；
- Author Truth 不作为独立文件自动注入 Chat；
- 运行时 World、NPC、Player、Quest、History Context 继续由后端构造；
- 保留当前结构化输出、文本输出和 Fallback 机制；
- 保留回复长度和安全边界，避免角色用一条回复倾倒整段设定；
- Chat 继续保持只读，不能替玩家推进任务或移动角色。

Prompt v3 的主要目标不是让模型“知道更多”，而是让不同角色**知道不同的内容，并以不同方式表达不确定性**。

## 13. Mock 内容增强

Mock Provider 仍然是离线验收和 Fallback 的正式组成部分，不应只返回通用占位句。

Phase 1E 计划补充以下高频意图：

- “你是谁”；
- “这里是哪里”；
- “我是谁 / 你认识我吗”；
- “我身上的印记是什么”；
- “终焉战争 / 魔王 / 古族是什么”；
- “灰烬战争发生了什么”；
- “晨曦城堡有什么”；
- “低语森林安全吗”；
- 当前失踪孩子任务相关问题。

同一问题必须得到符合角色立场的不同回答。例如对于“历史书可信吗”：

- Ryan 倾向相信骑士教育，但会因父亲经历产生迟疑；
- Shir 会指出档案缺口，却拒绝一次说尽；
- Grey 会承认记录并不完整，同时警告真相也会带来代价。

Mock 继续保持确定性、无网络、无随机行为和无状态写入。

## 14. `hy-role` 推荐与真实模型示例

基于当前项目的实际对话测试，`hy-role` 在角色一致性、对上下文的理解和自然语言表现上效果优秀。README 可将其写为：

> 基于本项目 NPC 角色对话的实际测试，推荐优先尝试 `hy-role`；项目仍通过统一 OpenAI-compatible Adapter 接入，不将业务层绑定到特定供应商。

不得写成“行业最聪明模型”“效果一定优于所有模型”等无法由本项目验证的绝对结论。

配置示例应遵循现有 Provider 能力，并明确 `hy-role` 使用文本输出模式：

```env
CHAT_PROVIDER=hunyuan
CHAT_LLM_BASE_URL=<OpenAI-compatible endpoint>
CHAT_LLM_MODEL=hy-role
CHAT_LLM_OUTPUT_MODE=text
CHAT_LLM_AUTH_MODE=bearer
CHAT_LLM_API_KEY=<your-api-key>
```

README 后续可加入一个简短的脱敏对话示例，但必须满足：

- 来自用户确认的本项目真实测试结果，或明确标注为“示意对话”；
- 不包含 API Key、Authorization Header、完整 Prompt 或完整响应日志；
- 最多展示一到两轮能够体现角色差异的问答；
- 不把一次示例包装成普遍性能评测；
- 不泄露 README 无剧透部分不应公开的 Author Truth。

## 19. 测试与验收策略

### 19.1 自动化测试

- Prompt v3 文件完整、角色可加载、未知角色安全失败；
- Prompt 上下文仍包含运行时 NPC、Player、Quest 与近期历史；
- 角色 Prompt 具有不同知识边界和语言规则；
- Mock 高频问题能够按角色返回不同回答；
- Mock 不进行网络访问和状态写入；
- `hy-role` 文本输出模式与现有 Adapter 解析路径兼容；
- Provider 失败仍返回可识别的 Mock Fallback；
- Quest 状态机、位置检查、NPC 在场检查保持原有行为；
- World Tick、NPC State、Action 和 Event 不因 Chat 内容改动而改变；
- Backend 全量测试通过；
- Frontend 类型检查、单元测试与构建通过。

### 19.2 文档与内容检查

- 全仓不混用“阿莱瑞亚”“曦谷城堡”等废弃名称；
- Grey 不被描述为终焉战争亲历者；
- 终焉战争与灰烬战争的时间和作用不混淆；
- Public Lore、Character Knowledge 与 Author Truth 没有越级泄露；
- README 不宣称未实现的职业、分支、地图或在线部署；
- `hy-role` 推荐表述有范围限定，示例已脱敏并经用户确认；
- README 首屏能够在约三十秒内回答“这是什么、能玩什么、为什么值得体验”。

### 19.3 人工体验验收

- Mock 模式下询问三位 NPC“你是谁”“这里是哪里”“历史可信吗”，回答有明显区分；
- 真实 Provider 模式下角色不会全知、不会替玩家推进任务；
- 完成失踪孩子任务后，玩家能够感知主线伏笔但不会得到完整真相；
- 新用户只阅读 README 即可在无 API Key 情况下启动并完成基础闭环。

## 20. 风险与控制

### 20.1 世界观过重，掩盖当前玩法

控制方式：README 只讲无剧透钩子；完整设定进入 Story Bible；当前任务只承担一个轻量伏笔。

### 20.2 模型因为掌握太多信息而剧透

控制方式：Author Truth 不注入；按角色拆分知识；Prompt 明确“未知、怀疑、隐瞒、禁止透露”四类边界。

### 20.3 NPC 人设只停留在形容词

控制方式：每位角色同时定义欲望、矛盾、错误认知、秘密、关系张力和语言行为，并用同题对话测试区分度。

### 20.4 文案修改意外破坏测试或任务

控制方式：状态与 ID 不变；先更新行为级测试，再修改实现；避免用长篇精确文本作为脆弱断言。

### 20.5 README 过度营销

控制方式：当前能力、实测观察和未来规划分区呈现；模型推荐限定在本项目角色对话场景；真实示例必须脱敏并经确认。

### 20.6 Prompt 体积膨胀

控制方式：公共信息只写一次；角色只携带自身必要知识；回复保持简洁；不向每次请求注入完整 Story Bible。

## 21. 阶段完成标准

Phase 1E 完成时，应达到以下效果：

- 项目拥有唯一可信、内部一致的中文 Story Bible；
- 玩家、地点、两场战争和三位 NPC 的设定不再互相冲突；
- 三位 NPC 在 Mock 和真实 LLM 模式下都具有可辨认的立场与声音；
- 当前任务自然连接失忆玩家和古老遗迹，但没有虚构新的系统能力；
- Chat 仍然只读，World Engine 仍然确定；
- README 能先讲好游戏，再讲清工程，并完整覆盖腾讯作业提交要求；
- `hy-role` 推荐配置和示例准确、脱敏、不过度承诺；
- 所有自动化测试和人工闭环验收通过；
- 所有修改均经过用户逐模块 Review 后由用户自行提交。
