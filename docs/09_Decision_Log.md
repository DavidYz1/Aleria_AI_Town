# Aleria AI Town 架构决策记录（Architecture Decision Record）

版本：v1.4

更新时间：2026-08-24

# 1. 文档目的

本文件用于记录 Aleria AI Town 项目中的关键技术与架构决策。

目标：

-   记录为什么选择某种方案
-   保留设计演进过程
-   方便后续开发维护
-   支持面试中的技术方案解释

本项目不仅关注功能实现，同时关注：

> 为什么这样设计，以及这种设计带来的工程权衡。

------------------------------------------------------------------------

# 2. 架构决策原则

Aleria AI Town 遵循以下原则：

## 2.1 MVP优先

项目目标：

在有限时间内完成：

-   可运行
-   可演示
-   可解释

因此避免过早引入复杂基础设施。

------------------------------------------------------------------------

## 2.2 世界模型优先

系统设计围绕：

World State

而不是：

单次请求。

核心流程：

    World State

    ↓

    NPC Agent

    ↓

    Action

    ↓

    Event

    ↓

    World Update

------------------------------------------------------------------------

## 2.3 AI增强而非AI替代

LLM不直接控制整个系统。

采用：

    规则约束

    +

    LLM生成

保证：

-   可控
-   可解释
-   可测试

------------------------------------------------------------------------

# 3. ADR-001：整体系统架构选择

## 背景

项目需要支持：

-   Web前端
-   后端API
-   世界模拟
-   NPC Agent
-   数据存储

考虑方案：

## 微服务架构

优点：

-   高扩展性

缺点：

-   部署复杂
-   开发成本高
-   不适合2-3天MVP

## 简单脚本架构

优点：

-   开发快

缺点：

-   模块耦合
-   后续扩展困难

------------------------------------------------------------------------

## 决策

采用：

> 模块化单体架构（Modular Monolith）

结构：

    Backend

    ├── API Layer

    ├── World Engine

    ├── Agent System

    ├── Database Layer

    └── LLM Provider

------------------------------------------------------------------------

## 原因

适合：

-   AI应用快速迭代
-   小团队开发
-   后续模块拆分

------------------------------------------------------------------------

# 6. ADR-004：数据库选择

## 候选方案

## Redis

问题：

主要用于缓存。

不适合作为长期世界状态存储。

------------------------------------------------------------------------

## MySQL/PostgreSQL

优点：

生产级。

缺点：

MVP部署成本更高。

------------------------------------------------------------------------

## SQLite

最终选择。

原因：

-   数据量小
-   单机运行
-   部署简单
-   满足Demo需求

同时：

通过Repository Layer隔离数据库。

未来可以迁移：

    SQLite

    ↓

    PostgreSQL/MySQL

# 7. ADR-005：NPC Agent架构选择

这是项目核心决策。

------------------------------------------------------------------------

## 方案一：纯规则系统

例如：

    if energy < 20:

        sleep

优点：

稳定。

缺点：

NPC行为固定，没有人格。

------------------------------------------------------------------------

## 方案二：纯LLM Agent

优点：

自由度高。

缺点：

-   行为不可控
-   可能违反世界规则
-   难测试

------------------------------------------------------------------------

## 决策

采用：

> Hybrid Agent（混合Agent）

架构：

    Rule Engine

    ↓

    Candidate Actions

    ↓

    LLM Decision

    ↓

    Action Validation

    ↓

    World Update

------------------------------------------------------------------------

## 原因

规则负责：

-   世界约束
-   合法性

LLM负责：

-   人格体现
-   行为解释
-   对话生成

------------------------------------------------------------------------

# 11. ADR-009：LLM Provider设计

## 问题

如果业务代码直接调用某个模型：

会导致：

-   模型绑定
-   难测试

------------------------------------------------------------------------

## 决策

设计统一接口：

    ChatProvider
         |
         |---- MockChatProvider
         |
         └---- FallbackChatProvider
                   ├── OpenAICompatibleChatProvider
                   └── MockChatProvider

Phase 1C 不为腾讯混元、DeepSeek、本地 Qwen 分别复制 Provider 类。它们通过 `base_url/api_key/model/auth_mode` 复用一个 compatible Adapter；未来非 compatible 协议再新增独立 Adapter。

------------------------------------------------------------------------

## 原因

支持：

-   多模型切换
-   无密钥运行
-   自动测试

# 15. ADR-012：Phase 0即使用SQLite

## 背景

Phase 0可以直接从JSON或内存返回世界数据，也可以从第一条API开始建立持久化边界。

## 决策

采用：

> SQLite作为运行时唯一状态源，根目录JSON只作为可读、可版本管理的种子输入。

Phase 0只创建 `world_state`、`locations`、`npc_profiles`、`npc_states` 四组表。

## 原因

-   尽早验证Repository边界。
-   为World Tick提供真实状态基础。
-   保持初始内容可读，同时避免JSON与SQLite形成两个运行时可信源。
-   控制物理表数量，不提前实现尚无用例支撑的Memory、Relationship和Snapshot。

------------------------------------------------------------------------

# 16. ADR-013：统一公共契约命名

## 决策

-   世界回合统一使用 `tick`。
-   NPC职业统一使用 `role`。
-   NPC当前位置统一使用 `location_id`。
-   NPC需求 `energy`、`mood`、`social` 统一为0-100整数。
-   World、Location和NPC统一使用稳定的小写字符串ID。
-   第一版Action集合统一为 `move`、`rest`、`work`、`eat`、`social`。

## 原因

避免API、数据库、Prompt、Validator和Frontend分别形成不兼容字段。

------------------------------------------------------------------------

# 17. ADR-014：开源前端迁移限定在展示层

## 决策

Frontend保持：

    Typed API Adapter
    ↓
    World Store
    ↓
    UI / Renderer

未来引入开源Vue界面、PixiJS或其他2D渲染方案时，只替换组件、样式、素材和Renderer，不以模板数据结构反向修改World API和Backend领域模型。

## 原因

-   保证Backend继续作为世界唯一状态源。
-   降低前端视觉迁移对Agent和数据层的影响。
-   可以独立审查开源许可证、素材授权和依赖风险。

------------------------------------------------------------------------

# 18. ADR-015：Phase 1A使用确定性同快照决策

## 决策

所有NPC在时钟推进和统一需求衰减后，从同一个不可变快照选择Action。决策只依赖当前状态、角色特点、morning/day/evening/night阶段与稳定 `sort_order`。

## 原因

-   同输入必然产生同输出，便于测试、演示和排错。
-   避免NPC数据库顺序或当前Tick执行顺序影响结果。
-   先验证世界规则闭环，后续Hybrid Agent只需替换Decision Policy。

------------------------------------------------------------------------

# 19. ADR-016：Tick使用expected_tick乐观锁与单事务

## 决策

Frontend提交当前 `expected_tick`；Backend通过条件更新保证同一版本只有一个请求成功。世界/NPC当前状态与Action/Event历史在一个事务中提交。

## 原因

防止重复点击或并发请求造成时间跳跃、部分NPC更新或重复历史。

------------------------------------------------------------------------

# 20. ADR-017：Tick返回完整World而非Patch

## 决策

成功响应返回完整 `WorldData + actions + events`。409时Frontend重新GET权威世界。

## 原因

保持Frontend Store简单，避免客户端自行合并状态导致契约漂移，也为后续替换UI/Renderer保留稳定边界。

------------------------------------------------------------------------

# 21. ADR-018：NPC Detail使用独立只读切片与确定性解释

## 背景

Phase 1B 需要展示 NPC 的权威当前状态和最近行动，同时不能破坏已经验证的确定性 Tick 写入路径，也不应把规则解释误表述为模型思维过程。

## 决策

-   新建 `NpcRepository → NpcService → GET /api/npcs/{npc_id}` 只读切片，不向 `WorldTickRepository` 添加详情查询。
-   复用 `npc_profiles`、`npc_states`、`locations`、`world_state`、`actions`，不新增数据库表。
-   数据库保留稳定 `actions.reason` 机器代码；Detail DTO 对外提供 `reason_code` 和根据历史上下文确定生成的 `reason_text`。
-   解释是可审计的规则摘要，不重算历史决策，不保存或暴露 chain-of-thought/Agent Trace。
-   Frontend 使用独立 `npcDetail` Store 处理选择、竞态、重试和刷新；`TownView` 协调 World/NPC Detail Store，两个 Store 不相互依赖。

## 原因

-   保护 Tick 的单事务写入边界，让详情查询可独立演进。
-   保持 Backend 作为状态与历史的唯一事实来源。
-   在可解释、可测试和不暴露隐藏推理之间保持清晰边界。

------------------------------------------------------------------------

# 22. ADR-019：真实模型使用单一 OpenAI-compatible Adapter

## 决策

`ChatService` 只依赖 `ChatProvider`。除 Mock 外的 Provider 标签统一由 `OpenAICompatibleChatProvider` 处理，配置为 `base_url/api_key/model/auth_mode/timeout`，不创建 Hunyuan、DeepSeek 或 Qwen 专用 Service 分支。

## 原因

-   避免供应商类重复和配置漂移。
-   同时支持云端 API 与本地 compatible 服务。
-   保留未来新增 Gemini native 等非 compatible Adapter 的能力。

------------------------------------------------------------------------

# 23. ADR-020：Mock 是一等运行模式与自动 fallback

## 决策

默认 `CHAT_PROVIDER=mock`，无 URL、model、Key 也能完成验收闭环。非 Mock Primary 的可预期 Provider 故障由 `FallbackChatProvider` 降级到真实 `MockChatProvider`，并如实返回和保存 `provider=mock`、`fallback_used=true`。

## 原因

-   腾讯作业可以在无外网、无密钥环境稳定演示和测试。
-   fallback 不伪装成 Primary 成功，便于诊断和 UI 提示。
-   仅捕获 `ChatProviderError`，不吞掉编程错误。

------------------------------------------------------------------------

# 24. ADR-021：Chat 与确定性 World Engine 隔离

## 决策

Chat Context 可以读取 World、NPC State 和最近 Action，但 Chat 路径不得调用 World Tick、更新 NPC State 或插入 Action/Event。聊天历史只进入后续 Chat Context，不影响 Phase 1A 的确定性 Action Policy。

## 原因

-   保持同输入世界快照产生同一 Action 的可重复性。
-   防止自然语言输出绕过 Action Validation 和事务边界。
-   未来 Memory/Relationship 进入世界决策前必须另行设计并审查。

------------------------------------------------------------------------

# 25. ADR-022：只原子保存完整聊天轮次

## 决策

Provider 调用发生在数据库写事务之外。只有回复通过严格 `reply + emotion` 校验后，Repository 才在一次事务中创建/更新 Conversation，并同时插入 User 与 Assistant；任一持久化错误整体回滚。

## 原因

-   Provider 或数据库故障不留下只有 User 的半轮记录。
-   Assistant 行可以保存实际 Provider、fallback 和 Prompt 版本，支持审计。
-   有界历史始终由完整的持久化消息构成。

------------------------------------------------------------------------
