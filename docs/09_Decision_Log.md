# Aleria AI Town 架构决策记录（Architecture Decision Record）

版本：v1.1

更新时间：2026-08-22

# 1. 文档目的

本文件用于记录 Aleria AI Town 项目中的关键技术与架构决策。

目标：

-   记录为什么选择某种方案
-   保留设计演进过程
-   方便后续开发维护
-   支持面试中的技术方案解释

本项目不仅关注功能实现，同时关注：

> 为什么这样设计，以及这种设计带来的工程权衡。

------------------------------------------------------------------------

# 2. 架构决策原则

Aleria AI Town 遵循以下原则：

## 2.1 MVP优先

项目目标：

在有限时间内完成：

-   可运行
-   可演示
-   可解释

因此避免过早引入复杂基础设施。

------------------------------------------------------------------------

## 2.2 世界模型优先

系统设计围绕：

World State

而不是：

单次请求。

核心流程：

    World State

    ↓

    NPC Agent

    ↓

    Action

    ↓

    Event

    ↓

    World Update

------------------------------------------------------------------------

## 2.3 AI增强而非AI替代

LLM不直接控制整个系统。

采用：

    规则约束

    +

    LLM生成

保证：

-   可控
-   可解释
-   可测试

------------------------------------------------------------------------

# 3. ADR-001：整体系统架构选择

## 背景

项目需要支持：

-   Web前端
-   后端API
-   世界模拟
-   NPC Agent
-   数据存储

考虑方案：

## 微服务架构

优点：

-   高扩展性

缺点：

-   部署复杂
-   开发成本高
-   不适合2-3天MVP

## 简单脚本架构

优点：

-   开发快

缺点：

-   模块耦合
-   后续扩展困难

------------------------------------------------------------------------

## 决策

采用：

> 模块化单体架构（Modular Monolith）

结构：

    Backend

    ├── API Layer

    ├── World Engine

    ├── Agent System

    ├── Database Layer

    └── LLM Provider

------------------------------------------------------------------------

## 原因

适合：

-   AI应用快速迭代
-   小团队开发
-   后续模块拆分

------------------------------------------------------------------------

# 6. ADR-004：数据库选择

## 候选方案

## Redis

问题：

主要用于缓存。

不适合作为长期世界状态存储。

------------------------------------------------------------------------

## MySQL/PostgreSQL

优点：

生产级。

缺点：

MVP部署成本更高。

------------------------------------------------------------------------

## SQLite

最终选择。

原因：

-   数据量小
-   单机运行
-   部署简单
-   满足Demo需求

同时：

通过Repository Layer隔离数据库。

未来可以迁移：

    SQLite

    ↓

    PostgreSQL/MySQL

------------------------------------------------------------------------

# 7. ADR-005：NPC Agent架构选择

这是项目核心决策。

------------------------------------------------------------------------

## 方案一：纯规则系统

例如：

    if energy < 20:

        sleep

优点：

稳定。

缺点：

NPC行为固定，没有人格。

------------------------------------------------------------------------

## 方案二：纯LLM Agent

优点：

自由度高。

缺点：

-   行为不可控
-   可能违反世界规则
-   难测试

------------------------------------------------------------------------

## 决策

采用：

> Hybrid Agent（混合Agent）

架构：

    Rule Engine

    ↓

    Candidate Actions

    ↓

    LLM Decision

    ↓

    Action Validation

    ↓

    World Update

------------------------------------------------------------------------

## 原因

规则负责：

-   世界约束
-   合法性

LLM负责：

-   人格体现
-   行为解释
-   对话生成

------------------------------------------------------------------------

# 15. ADR-012：Phase 0即使用SQLite

## 背景

Phase 0可以直接从JSON或内存返回世界数据，也可以从第一条API开始建立持久化边界。

## 决策

采用：

> SQLite作为运行时唯一状态源，根目录JSON只作为可读、可版本管理的种子输入。

Phase 0只创建 `world_state`、`locations`、`npc_profiles`、`npc_states` 四组表。

## 原因

-   尽早验证Repository边界。
-   为World Tick提供真实状态基础。
-   保持初始内容可读，同时避免JSON与SQLite形成两个运行时可信源。
-   控制物理表数量，不提前实现尚无用例支撑的Memory、Relationship和Snapshot。

------------------------------------------------------------------------

# 16. ADR-013：统一公共契约命名

## 决策

-   世界回合统一使用 `tick`。
-   NPC职业统一使用 `role`。
-   NPC当前位置统一使用 `location_id`。
-   NPC需求 `energy`、`mood`、`social` 统一为0-100整数。
-   World、Location和NPC统一使用稳定的小写字符串ID。
-   第一版Action集合统一为 `move`、`rest`、`work`、`eat`、`social`。

## 原因

避免API、数据库、Prompt、Validator和Frontend分别形成不兼容字段。

------------------------------------------------------------------------

# 17. ADR-014：开源前端迁移限定在展示层

## 决策

Frontend保持：

    Typed API Adapter
    ↓
    World Store
    ↓
    UI / Renderer

未来引入开源Vue界面、PixiJS或其他2D渲染方案时，只替换组件、样式、素材和Renderer，不以模板数据结构反向修改World API和Backend领域模型。

## 原因

-   保证Backend继续作为世界唯一状态源。
-   降低前端视觉迁移对Agent和数据层的影响。
-   可以独立审查开源许可证、素材授权和依赖风险。
