## 读数说明（人工补充，非脚本输出）

**1. §17.5 通过：动作合法率 100.0%（43/43）。** 43 条模型产出的计划步骤无一被
`ActionRegistry` 替换，`rule_rejection` trace 为空。对照 2026-09-14 的 90.2%（37/41）
——那次刚好压在验收线上，且其中 4 条被拒。本次样本更大且零拒绝。

**2. 失败归因第一次出现两个类别，而它们的耗时特征完全相反：**

```
provider:http_status  3 次   耗时 2328 / 2585 / 2128 ms     ← 约 2 秒快速失败
provider:timeout     14 次   耗时 30008 … 30023 ms          ← 等满 30 秒
```

**这正是拆分 taxonomy 的意义。** 在旧的合并实现下，这 3 次会和超时混在一起，读数
的人会得出「继续调高超时」的结论——但它们是服务端主动拒绝，再等多久都不会成功。
两类需要完全不同的应对：超时看上限与模型速度，HTTP 错误看配额、限流与重试策略。

**3. 超时上限 30 秒仍在切东西，但边际收益已明显下降。** 12 次成功调用的耗时是
`10023 / 10128 / 10932 / 11316 / 11888 / 12945 / 13308 / 14095 / 15447 / 19527 /
23592 / 24197 ms`——**只有 2 次超过 20 秒**，其余都在 20 秒内完成。而 14 次超时全部
等满 30 秒。这与 5 tick 探路时「6 次成功有 3 次超过 20 秒」的比例不同，说明本次服务端
对**能返回的请求**响应更快。继续加大上限（如 45 秒）不太可能再有 20→30 那样的收益，
应该先查那 14 次为什么根本没返回。

**4. 一个未记录的细节：`http_status` 没有区分具体状态码。** 2 秒内失败、且与 14 次
超时同期出现，符合服务端限流或过载的特征（29 次调用集中在约 7 分钟内发出），但
**当前 trace 无法确认是 429 还是 5xx**。这是下一个可以细化的观测点——状态码本身不敏感，
可以安全记录。**不要在这份报告的基础上断言"是限流"。**

**5. 计划复用把 4 个 tick 变成了近乎零成本。** 20 个 tick 里有 4 个耗时 < 1 秒
（最快 0.1s），因为三个 NPC 全部复用已有计划、零模型调用。tick 耗时 P50 14.213s，
最慢 35.5s。复用率 51.7%（31/60），模型调用降到 0.483 次/NPC-tick。

**6. 行为熵 2.126 / 2.585 是历次最高**（Fake 1.411、5 tick 探路 1.555 与 1.930）。
动作分布 `rest 19、move 16、work 15、talk 6、eat 4` 覆盖 6 个动词里的 5 个，
`wait` 未出现。分布均衡说明没有行为坍缩。

**7. 仍然偏低的一项：可用决策率 41.4%（12/29）。** 这不影响 §17.5——合法率衡量的是
「拿到结果之后对不对」，可用率衡量的是「拿没拿到」，两者是并列的两个分母。但它说明
真实模型的可用性仍是当前最大瓶颈，且瓶颈主要在服务端（14 次超时 + 3 次 HTTP 错误），
不在提示词或动作契约。

**8. 成本**：29 次调用，已上报 token 39553（覆盖 12/29）。失败的 17 次未返回 usage，
实际服务端消耗未知，**不能把 39553 当作本次评测的总成本**。
