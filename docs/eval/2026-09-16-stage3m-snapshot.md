**本次最有价值的发现：两类失败的耗时特征完全相反。**

```
provider:http_status  3 次   2328 / 2585 / 2128 ms     ← 约 2 秒快速失败
provider:timeout     14 次   30008 … 30023 ms          ← 等满 30 秒
```

在旧的合并实现下这 3 次会被算进超时，读数的人会得出「继续调高超时」的结论——
但它们是服务端主动拒绝，再等多久都不会成功。**两类需要完全不同的应对。**
这是拆分 taxonomy 最直接的回报。

**超时上限的边际收益已明显下降**：12 次成功里只有 2 次超过 20 秒（5 tick 探路时是
6 次里 3 次）。继续加大上限不太可能再有 20→30 那样的效果，应该先查那 14 次为什么
根本没返回。

**下一个观测点**：`http_status` 未区分具体状态码。2 秒内失败且与超时同期出现，符合
限流或过载特征（29 次调用集中在约 7 分钟内），但当前 trace 无法确认是 429 还是 5xx。
状态码本身不敏感，可以安全记录。**不要据现有数据断言「是限流」。**

### 第三次探路：超时上限 20 → 30 秒

完整报告见 [timeout-30 探路](2026-09-17-agent-eval-live-probe-timeout30.md)。唯一改动是
本地 `.env` 的 `PLANNING_PROVIDER_TIMEOUT_SECONDS`（`Settings` 默认值仍为 20.0）。

**一条不依赖对比的直接证据**：6 次成功调用里有 **3 次耗时超过 20 秒**
（20113 / 20970 / 23959 ms）——它们在旧上限下必然被判超时。上一轮只能说明「撞到了
上限」，这一轮才回答了「撞上限的那些再等一会儿会不会成功」：会。

| 指标 | 20 秒 | 30 秒 |
| --- | --- | --- |
| 可用决策率 | 27.3%（3/11） | **85.7%（6/7）** |
| 兜底率 | 53.3%（8/15） | **6.7%（1/15）** |
| 计划复用率 | 26.7%（4/15） | **53.3%（8/15）** |
| 模型调用 / NPC-tick | 0.733 | **0.467** |
| 行为熵 | 1.555 | **1.930** |
| 动作种类 | 4 种 | **5 种** |
| tick 耗时 P50 | 20.225s | 20.382s |
| tick 耗时 P95 | 20.607s | **30.302s** |

**二阶效应值得单独记一笔：提高超时反而减少了模型调用。** 机制是一个被打断的恶性循环——
超时 → 兜底 → 本 tick 没产生计划 → 下个 tick 必须重新规划 → 更多调用、更多超时机会。
成功的规划会产出可跨 tick 复用的计划，调用次数因此自然下降。设计超时策略时容易忽略这点。

**代价落在 P95 不在 P50。** 逐 tick 是 `30.3 / 24.1 / 10.3 / 0.1 / 20.4` 秒，其中 0.1s
那个 tick 三个 NPC 全部复用计划、零调用。平均体感改善，变差的是最坏情况。

**仍然不能声称的**：5 tick、单次运行、外部服务不可控。上表第 1 条是直接观测，但
「27.3% → 85.7%」这个幅度里有多少来自超时调整、多少来自服务端波动，本轮数据无法区分。

### 三条来自本次数据的补充观察

**计划步数是「减少模型调用」里最便宜的杠杆，且尚未测过。** 30 个计划覆盖 60 个
NPC-tick，即平均每个计划只被消费 **2 步**。`agent_plans` 的契约允许 1–4 步，
HEAD `5bc8858` 也已经在 prompt 里要求「prefer multi-step plans」。如果真实模型稳定
产出 4 步，调用数可从 0.500 降到约 0.25 次/NPC-tick，**不需要任何架构改动**。
但 Fake 的步数由替身写死，这个分布在真实模型下是多少**本轮未测** —— 应该在下次 Live
评测里直接统计 `agent_plans.steps_json` 的长度分布，再决定要不要调 prompt。

**`max_plan_age_ticks = 8` 目前是一条不生效的保护。** 30 个计划里 27 个
`completed`、3 个 `active`，**0 个 abandoned**。过龄放弃是为了防止 NPC 抱着过期计划
不放，但 2 步的计划远够不到 8 tick 的窗口。只有当上一条把计划拉长之后，这个参数才会
真正开始工作 —— 两件事应该一起评估，不要单独调这个数字。

**加大并行是负收益方向，应明确排除。** `MAX_PLANNING_WORKERS = 8` 而 NPC 只有 3 个，
并行度本就过剩。`.superpowers/sdd/2026-09-15-planning-latency-diagnostic/` 的历史诊断
更进一步：并发反而把单次调用延迟拉长约 3 倍（服务端吞吐受限），三个假设（放宽超时、
连接池、单 tick 调用数上限）均被证伪。客户端侧的杠杆已基本用尽，真正的答案是把规划
移出 tick 的关键路径 —— 也就是上表的 P2 架构项，而不是继续加线程。

**公开 Demo 风险优先于性能优化**：现有共享世界的匿名全局 Reset、无账号隔离及 HTTP 入口不适合公开收集真实用户对话。对外展示前应至少限制 Reset 权限、提供 TLS 并明确数据保留策略；这些涉及权限与生产运行模型，需单独设计和确认，不能作为本轮小改直接合入。
